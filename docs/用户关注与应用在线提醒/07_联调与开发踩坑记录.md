# 07 — 联调与开发踩坑记录

> 本文记录“关注动态 + 应用在线提醒”在桌面端、Rust Agent、`neko-server` 和 Dev UI 联调中已经踩过的坑。后续继续开发或联调前，请先快速扫一遍，避免重复犯错。

## 固定环境事实

- 测试服务器固定使用 `https://nekostatus.koirin.com`，Dev 首次配置、默认生产地址、联调脚本和文档示例都不得回退到旧地址。
- 线上 `neko-server` 源码映射盘是 `Z:\NF\neko-server`，真实路径是 `E:\NF\neko-server`。
- `Z:` 适合查看和小范围编辑，不适合跑 Next 构建；构建、类型检查、重启、端口确认优先通过 SSH 在服务器本机执行。
- 服务器资源不足时，已获得授权可暂停 `neko-server` 进程；只允许停止 `E:\NF\neko-server` 对应的 Node/7452 进程，不要碰其他业务进程。

## 服务端联调坑

- Presence 请求体里的 `state` 是 `active / heartbeat / hidden / idle / offline`；`activity.entered` 是事件类型，不是请求状态。不要把 `entered` 发到 `/api/activity/presence`。
- 新检测到的应用默认 `isHidden=true`，不会进入关注者目录、当前状态或事件。发布方必须显式公开应用后，关注者才能添加提醒规则。
- 关注者手填 `.exe` 不能绕过发布方公开规则。服务端应拒绝缺失或隐藏的目标应用，典型错误是 `APP_HIDDEN_BY_TARGET`。
- 同一用户同一应用多设备在线按用户级合并，只通知一次；验证时要确认 session source 里能看到来源设备，而不是期望两条通知。
- `/api/v2/status/report` 是旧状态上报链路，不能用普通 JSON 当作有效烟测。要验证旧链路不受影响，应使用它期望的 multipart/设备密钥路径，或只做“路由仍返回 API 错误而非崩溃”的轻量检查。
- 拉黑后必须立即撤销双方关注、规则、当前状态与本地缓存；搜索结果双方互相不可见。
- SSE 验证要同时看首连 `text/event-stream`、断线恢复和轮询降级；只看到 HTTP 200 不等于联调完成。
- API 客户端必须禁止跟随登录页重定向并验证 Content-Type/schema；`200 text/html` 不是 Activity API 成功。生产路由、中间件和公网反代恢复步骤见 [10_连接健康状态与服务端恢复清单.md](./10_连接健康状态与服务端恢复清单.md)。
- 活动快照上传发生在 presence 之前，因此目标应用必须已经存在于发布方目录且为公开状态；首次检测出的默认隐藏应用不会上传快照。
- 旧 Agent Token 没有 `snapshot:write` 属于正常兼容场景，应降级无图，重新 Provision 后才获得新 scope。
- 快照文件必须放在服务端私有目录，不能放进 Next `public/`；只靠难猜 UUID 不是权限控制。
- 删除过期 `ActivitySnapshot` 记录时必须同步删除私有图片文件，避免磁盘持续增长。

## Dev 客户端坑

- “公开当前应用”不能用点击按钮后的 `getActiveWindow()`。用户点击按钮时，Neko 本身已经成为前台，必然容易把 `NekoStatusDev.exe` 填进去。
- 正确交互应复用隐私功能的窗口框选：隐藏 Neko 主窗口，弹出透明选择层，用户点选目标窗口后只取 `.exe` 进程名。
- 活动功能不上传窗口标题。选窗层可以本地显示窗口标题帮助识别，但表单、日志、服务端请求和文档都不能把标题当作活动数据。
- 面包屑里的英文副标题不是问题；真正要避免的是内容区再放一个同级重复标题。推荐面包屑 `关注动态 / Following Activity`，内容区标题用“应用上线提醒”等场景化名称。
- 活动页文案要面向用户，不要把默认说明写成“代理、PID、协议、SSE”等程序员视角；这些信息只放到“诊断信息”折叠区。
- 开关保存要有等待态和失败回滚。网络慢时不能假成功，失败后必须恢复上一次状态并给出页面内提示。
- 快照开关同时涉及本地配置、服务端 `shareSnapshots` 和 Agent Profile；Agent 同步失败时要补偿回滚服务端偏好。
- 不要在 presence 心跳里重复截图。快照只在新的稳定进入 transition 上准备一次，重试复用同一个 `snapshotId`。
- Toast 图片必须先下载到当前用户缓存后传本地路径；图片失败只能降级，不能阻止事件游标推进。
- Presence `sequence` 由服务端按设备持久化比较，Agent 重启后不能从 0 重新计数。使用启动时的 Unix 毫秒作为基线，再按请求递增，避免重启后的新状态被当作旧包拒绝。
- `sequence` 使用 JSON number 时必须满足 `Number.isSafeInteger`；超过 `9007199254740991` 必须发送十进制字符串，服务端上限为 signed BIGINT。不能先转成不安全的 JavaScript number 再 stringify。
- 同一版本通道、同一 Windows 登录用户只能运行一个 Presence Agent，因为互斥锁和命名管道是用户级唯一。开发版与正式版使用独立 pipe、mutex 和 profile；同一通道的双账号联调仍需隔离 userData，并串行交接 Agent。
- 隔离联调可传绝对路径 `NEKO_USER_DATA_DIR`。显式覆盖时不得迁移日常配置；测试完成后必须删除临时目录和凭据。
- Windows Toast 的 AppUserModelID 必须与开始菜单快捷方式注册值一致。开发身份是 `com.koirin.neko-status.dev`，正式 Agent Toast 使用 `com.koirin.neko-status`；本地验收正式 Toast 时要用匹配的正式身份启动，生产安装包天然满足这一条件。

## 实验性功能设置坑

- 设置页的“实验性功能”只放总开关和各实验功能入口开关；不要把所有实验功能的具体配置塞在设置页下面。
- 直播推流的 SRS、RTMP、OBS 配置属于直播推流页，不属于设置页实验区。
- 实验入口开关只控制入口和页面是否显示，不等于启用后台能力。关注动态的实际启用、分享、后台运行和开机启动仍在关注动态页里配置。
- 旧配置兼容：如果用户之前已经开启实验性内容，但没有新的入口开关键，应保留原先可见入口，避免升级后页面突然消失。
- 如果关注动态已经真正启用，侧边栏入口应保留；否则用户可能找不到关闭后台能力的入口。

## 线上构建与发布坑

- 服务端类型检查优先单独跑 `npx tsc --noEmit --pretty false`，不要把 TypeScript 错误误判成构建资源不足。
- Next 16 构建如遇 Turbopack 原生崩溃，可使用 `npx next build --webpack` 验证生产构建路径。
- 构建前后都要确认 7452 监听进程、`.next/BUILD_ID` 和公网接口；源码改了不等于线上已加载。
- 临时联调账号、设备、Agent Token 和测试应用数据必须按前缀或记录 ID 清理。验证完成后确认数据库里不再残留 `codexact` 等临时用户和设备。

## 回归检查清单

- Dev 默认地址和首次配置提示都指向 `https://nekostatus.koirin.com`。
- 活动页公开应用按钮调用窗口选择 IPC，不再调用 `getActiveWindow()`。
- 选择窗口后只填入进程名，显示名默认由进程名推导，窗口标题不进入持久化。
- 设置页实验区只看到入口开关；直播推流页内能看到并保存 SRS 配置。
- 关注动态入口和直播推流入口的显隐不会留下侧边栏空白，也不会让当前 active 页面卡在隐藏页。
- `npm run verify`、`npm run validate:agent` 通过后，再打开 Dev 做手工 UIUX 验收。
- 快照联调要额外确认：进程匹配、隐私规则、512KiB 上限、非接收者 403、关闭分享后的读取拒绝和 48 小时客户端缓存清理。
- 双账号验收结束后确认测试用户、设备、事件、快照数据库记录、私有图片文件和本地 Agent 缓存都已清理。
