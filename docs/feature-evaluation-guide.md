# 新功能评估与拆解流程

本文用于 Neko Status 新增功能前的立项、评估、拆解和交付准备。它更偏项目管理入口，回答“这个功能是否值得做、应该做到什么程度、怎么拆给团队或开发 agent、怎样验收”。进入编码实现后，再遵循 `docs/feature-lifecycle.md`、`docs/ipc-contract.md`、`docs/frontend-guideline.md` 和 `docs/testing-guideline.md`。

## 适用范围

以下情况必须先走本流程：

- 新增用户可感知的页面、控件、配置、后台能力或发布能力。
- 修改现有功能的核心行为、默认值、权限边界或失败处理。
- 新增或调整 IPC、preload、主进程服务、系统能力、后端 API 对接。
- 功能会影响打包、更新、登录、截图、推流、设备状态、公告、配置持久化等关键链路。
- 开发任务需要交给多人、外部团队或开发 agent 执行。

以下情况可以简化处理，但仍需写清验收标准：

- 单纯文案修正。
- 明确的小范围样式修复。
- 已有功能的低风险 bugfix。
- 不改变用户行为的局部重构。

## 核心产出

每个新功能在进入开发前，至少应产出以下内容：

| 产出物 | 目的 | 推荐位置 |
| --- | --- | --- |
| 功能简述 | 说明用户目标、背景、范围和价值 | issue、任务文档或 PR 描述 |
| 决策结论 | 说明做、不做、延后、降级或拆分 | issue、任务文档 |
| 验收标准 | 让开发、测试和 review 有共同判断口径 | issue、任务文档 |
| 技术影响评估 | 明确涉及 main/preload/renderer/shared/tests/docs 的范围 | issue、任务文档 |
| 任务拆解 | 拆成可独立实现、验证和 review 的工作项 | issue、任务看板 |
| 测试计划 | 明确自动化、手工、smoke、构建验证方式 | issue、PR 描述 |
| 发布与回滚方案 | 明确版本、开关、兼容、失败兜底和回滚方式 | issue、PR 描述、发布文档 |

## 角色分工

- 项目负责人：判断优先级、范围、版本目标和是否进入开发。
- 产品/需求提出方：说明用户问题、使用场景、成功标准和不做的代价。
- 技术负责人：判断实现路径、风险、依赖、测试策略和兼容边界。
- UI/UX 负责人：确认交互、文案、状态、错误提示和可访问性。
- QA/测试负责人：定义验收用例、回归范围和失败场景。
- 开发 agent：在信息完整后按任务拆解实现，开发前不得跳过契约、测试和文档判断。

小团队或单人开发时，可以由同一人承担多个角色，但对应问题仍要回答。

## 阶段 1：需求输入

需求提出时，必须先写清以下问题：

```text
功能名称：
提出人：
目标版本：
目标用户：
用户问题：
期望结果：
不做的影响：
已知限制：
参考资料或截图：
```

需求描述应聚焦用户目标，不要直接写成代码任务。例如优先写“用户需要在更新失败时知道失败原因并能重试”，而不是“加一个按钮调用 update check”。

## 阶段 2：初步分级

按优先级判断是否进入评估：

| 等级 | 判断标准 | 处理方式 |
| --- | --- | --- |
| P0 | 阻断启动、更新、登录、安全、核心数据或发布 | 立即评估，优先修复或降级 |
| P1 | 明显影响主要工作流，但有临时替代方式 | 纳入当前或下个版本 |
| P2 | 改善效率、体验、可维护性 | 排期开发，允许拆小 |
| P3 | 锦上添花、实验性或不确定收益 | 进入 backlog 或实验开关 |

再按工作类型分类：

- 用户功能：页面、控件、交互、状态展示。
- 系统能力：截图、窗口、托盘、文件、通知、权限。
- 数据与配置：持久化、默认值、迁移、导入导出。
- IPC/API：跨进程契约、后端接口、payload schema。
- 发布能力：更新源、安装器、版本、release notes。
- 工程能力：测试、构建、日志、开发者工具、文档。

## 阶段 3：范围定义

明确本次做什么，也明确不做什么。

必须写清：

- 功能入口在哪里：页面、弹窗、菜单、开发者控制台或自动流程。
- 用户可以执行哪些操作。
- 成功状态如何展示。
- 失败状态如何展示。
- 空状态、加载中、取消、超时、权限不足如何处理。
- 是否需要保存配置或记住用户选择。
- 是否需要兼容旧配置、旧 IPC 或旧版本数据。
- 是否需要新增日志、诊断信息或开发者命令。
- 哪些需求明确不在本次范围内。

范围不清时不要进入开发。可以先拆成“最小可交付版本”和“后续增强”。

## 阶段 4：技术影响评估

按项目结构逐项检查影响面：

| 层级 | 评估问题 |
| --- | --- |
| main | 是否需要主进程服务、系统能力、文件访问、网络请求、更新/安装逻辑 |
| ipc | 是否需要新增 channel/event，是否需要 schema，返回结构是否统一 |
| preload | 是否需要暴露新方法，是否保持最小能力面 |
| renderer service | 页面是否通过 `src/renderer/js/services/*` 调用能力 |
| renderer page/component | 是否需要新页面、新组件、状态管理或路由入口 |
| shared | 是否需要新增 `ipc-contracts.js`、`schemas.js` 或共享 helper |
| config | 是否需要默认值、迁移、兼容旧配置、敏感字段隔离 |
| docs | 是否影响功能生命周期、IPC、测试、发布或 UIUX 文档 |
| tests | 是否需要单元测试、renderer VM 测试、Electron smoke 或构建验证 |

涉及 IPC 时，必须先设计契约，再写 UI。涉及配置时，必须先设计默认值和迁移。涉及系统能力时，必须明确失败路径，不能只验证成功路径。

## 阶段 5：风险评估

至少从以下维度判断风险：

| 风险项 | 需要回答的问题 |
| --- | --- |
| 用户风险 | 是否可能误导用户、造成数据丢失、重复操作或错误状态 |
| 安全风险 | 是否涉及 token、文件路径、权限、shell、网络请求或外部 URL |
| 兼容风险 | 是否破坏旧配置、旧 IPC、旧安装包或旧 release 规则 |
| 稳定性风险 | 是否引入定时任务、后台循环、重试、并发或长耗时操作 |
| UI 风险 | 是否有多状态、多弹窗、条件型 UI 或移动/小窗口布局问题 |
| 测试风险 | 是否难以自动化，需要开发场景命令或手工验收 |
| 发布风险 | 是否影响安装器、自动更新、版本回滚或发布资产 |

风险评估结论必须落到处理动作：

- 接受：风险低，按正常流程开发。
- 降级：先做更小范围或关闭部分能力。
- 加保护：增加开关、权限判断、schema、超时、回滚或日志。
- 延后：依赖不成熟或收益不足，暂不开发。

## 阶段 6：方案设计

方案设计应包含：

```text
推荐方案：
备选方案：
为什么选择推荐方案：
涉及文件或模块：
新增/修改的 IPC：
新增/修改的配置：
UI 状态列表：
失败与回滚策略：
测试入口：
```

方案要尽量贴合现有架构：

- 新主进程能力优先放在 `src/main/*-service.js`、`src/main/system-utils.js` 或 `src/main/ipc/*.ipc.js`。
- 新 IPC 先更新 `src/shared/ipc-contracts.js` 和 `src/shared/schemas.js`。
- preload 只暴露最小必要方法。
- renderer 页面通过 `services/*` 调用，不直接拼 IPC channel。
- 页面逻辑放在 `src/renderer/js/pages/*.page.js`，可复用行为放在 `components/*`。
- 新增页面或模块后，同步检查 `scripts/verify.js` 是否需要纳入结构或语法验证。

## 阶段 7：任务拆解

任务要拆成可以独立交付和 review 的小块。推荐顺序：

1. 契约与数据：IPC constants、schema、配置默认值、迁移规则。
2. 主进程能力：service、system helper、IPC handler、错误结构。
3. preload 桥接：最小方法暴露、兼容处理。
4. renderer service：业务命名方法、调用封装、返回值兼容。
5. UI 实现：页面、组件、状态、文案、错误和空状态。
6. 测试：单元测试、renderer VM、smoke、开发场景命令。
7. 文档：功能说明、IPC、测试、发布、生命周期同步。
8. 发布准备：版本影响、release notes、回滚方案。

每个任务项建议写成：

```text
任务：
目标：
涉及文件：
完成标准：
验证方式：
依赖项：
风险：
```

## 阶段 8：验收标准

验收标准必须具体、可观察、可测试。不要只写“功能正常”。

推荐格式：

```text
给定：
当：
那么：
验证方式：
```

示例：

```text
给定：用户配置了一个不可访问的更新源
当：用户点击手动检查更新
那么：更新页展示失败原因，不覆盖其他已保存更新源，并允许用户重试
验证方式：单元测试覆盖 helper，手工验证更新页失败提示，运行 npm run verify
```

验收标准至少覆盖：

- 正常成功路径。
- 至少一个失败路径。
- 配置保存或兼容路径。
- UI 初始、加载、完成、错误状态。
- 相关日志或诊断出口。
- 文档和测试是否同步。

## 阶段 9：测试计划

根据影响面选择测试：

| 影响范围 | 最低测试要求 |
| --- | --- |
| shared schema / helper | 单元测试 |
| IPC channel / handler | IPC 注册和 handler 单元测试 |
| preload / bridge | 单元测试或 smoke，必要时 `npm run test:smoke` |
| renderer service | renderer service VM 测试 |
| 页面交互 | 页面 VM 测试或明确手工验收步骤 |
| 系统能力 | 单元测试加真实环境手工验收 |
| 更新/安装/发布 | `npm run verify`，必要时 `npm run build:zip` |

常用验证命令：

```bash
npm run verify
npm run test:smoke
npm run build:zip
```

如果某项无法自动化，必须写明原因、手工步骤和观察结果。

## 阶段 10：发布与回滚

进入开发前需要判断：

- 是否需要版本号或 release notes。
- 是否需要功能开关或实验入口。
- 是否会影响旧版本升级到新版本。
- 是否有配置迁移和迁移失败兜底。
- 是否能通过关闭入口、回滚配置或回退版本恢复。
- 是否需要给用户展示已知限制或失败提示。

高风险功能建议默认提供：

- 可关闭入口。
- 兼容旧配置。
- 结构化错误码。
- 开发者控制台诊断命令。
- 回滚说明。

## 阶段 11：开发 agent 执行要求

开发 agent 接到新功能任务时，必须先检查本流程是否已有结论。

如果信息完整，按以下顺序执行：

1. 复述功能目标、范围、验收标准和风险。
2. 阅读相关文档与代码落点。
3. 先实现契约、schema、配置和测试基础。
4. 再实现 main/preload/renderer service/UI。
5. 补齐测试、文档和验证命令。
6. 汇报改动、验证结果、残余风险。

如果信息缺失，agent 应先补充评估，而不是直接猜测实现。只有在低风险且范围明确时，才可以基于合理假设继续开发，并在最终说明中标记假设。

## 评估结论检查清单

进入开发前，负责人应确认：

- [ ] 用户目标清楚。
- [ ] 范围和不在范围清楚。
- [ ] 优先级和目标版本清楚。
- [ ] 技术影响面清楚。
- [ ] IPC、配置、系统能力和发布影响已评估。
- [ ] 风险有对应处理动作。
- [ ] 任务拆解可以独立执行。
- [ ] 验收标准可测试。
- [ ] 测试计划覆盖成功和失败路径。
- [ ] 文档同步范围明确。
- [ ] 回滚或降级方式明确。
