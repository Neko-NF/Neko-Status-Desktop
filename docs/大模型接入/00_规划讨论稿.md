# 00 — 大模型接入规划讨论稿

> 角色口径：产品经理向负责人汇报  
> 状态：待评审  
> 日期：2026-06-09

## 一、背景判断

Neko Status 当前核心价值是“采集、上报、展示和排障 Windows 设备状态”。项目已经有设备状态、截图隐私、上报服务、更新系统、推流、公告、开发者控制台和后端联调能力。

大模型接入不应该被做成泛聊天窗口。更适合贴合产品已有场景，解决三个真实问题：

- 用户看不懂状态和错误：例如上报失败、更新源异常、截图被跳过、权限不足。
- 开发和支持排障成本高：日志、健康检查、配置、最近上报结果分散在多个页面。
- 配置选择复杂：上报间隔、截图间隔、隐私规则、更新源模式、通知和勿扰设置需要解释和建议。

## 二、性能与工程约束

从现有性能和架构文档看，需要遵守以下约束：

- Electron v1 已有常驻内存 150~300MB 的历史问题，v2/Tauri 规划目标是常驻内存 ≤ 50MB；第一期不应引入本地模型常驻推理。
- 所有网络、文件、系统能力都必须在主进程处理，renderer 只能通过 preload 暴露的白名单 API 调用。
- 新后台能力不能耦合进状态上报 tick，避免模型超时、限流或供应商故障影响核心上报。
- 长耗时请求必须有超时、取消、并发限制和结构化错误。
- 条件型 UI 必须有可复现的开发入口或测试路径，不能只靠真实异常触发。
- 开发者控制台只能走白名单命令，不能把用户输入拼成 Shell、PowerShell、JavaScript 或动态 IPC channel。

## 三、推荐产品方向

推荐第一期做 **智能诊断助手**，而不是“全能聊天助手”。

### MVP 能力

1. **状态解释**
   - 汇总当前服务状态、最近一次上报、CPU/内存、电池、网络连通性、截图跳过原因。
   - 输出“当前是否正常、异常原因、建议下一步”。

2. **故障排查**
   - 用户主动点击“生成诊断”或在开发者控制台输入 `llm diagnose`。
   - 采集最近日志、健康检查、配置摘要、更新源诊断摘要。
   - 发送前展示上下文预览和敏感字段脱敏结果。

3. **配置建议**
   - 基于当前配置和最近状态，建议上报间隔、截图间隔、自动重启、隐私范围、通知设置。
   - 只给建议，不自动改配置。

4. **联调辅助**
   - 面向开发者控制台，解释 API 连接失败、IPC 缺失、更新源异常等常见问题。

### 明确不做

- 不做本地模型下载、启动和推理。
- 不上传截图原图或完整 base64。
- 不自动执行修复动作。
- 不做后台持续对话、持续监控或定时扣费调用。
- 不做服务端全量设备群体分析。
- 不把模型回答作为安全、医疗、法律、财务等高风险决策依据。

## 四、方案选型

### 推荐方案：主进程直连兼容 API，预留服务端代理

第一期在桌面端主进程实现通用 LLM provider adapter，支持用户配置 endpoint、model 和 key。后续可平滑切到服务端代理，由服务端统一鉴权、限额、审计和成本控制。

优点：

- 对当前桌面端改动闭环，不阻塞服务端开发。
- 用户可以先用自己的 API Key 验证价值。
- 主进程已有 Node 22 `fetch` 能力，接入成本低。
- 保留服务端代理扩展位，后续可做团队级预算和统一模型。

风险：

- 本地保存模型 API Key，需要更严格的安全存储与脱敏。
- 不同供应商的响应格式有差异，需要 adapter 层隔离。
- 费用由用户或团队承担，需要 UI 明确提示。

### 备选方案 A：只走服务端代理

优点是密钥不下发、成本可控、审计集中。缺点是需要服务端同步改造，排期更长，而且本地开发测试依赖服务端。

### 备选方案 B：本地模型

优点是隐私更强。缺点是包体、内存、启动耗时、硬件要求和模型管理成本都高，和当前轻量化方向冲突。建议至少放到 v2/Tauri 后再重新评估。

## 五、建议里程碑

| 阶段 | 目标 | 交付物 |
| --- | --- | --- |
| Phase 0 | 评审和范围确认 | 本目录文档、决策记录 |
| Phase 1 | MVP 只读诊断 | 设置项、主进程 LLM service、IPC、诊断面板、控制台命令、测试 |
| Phase 2 | 服务端代理与团队能力 | 服务端 `/api/ai/*`、配额、审计、管理员配置 |
| Phase 3 | 半自动修复建议 | 生成配置变更草案，用户确认后应用 |
| Phase 4 | v2/Tauri 适配 | Rust service adapter、轻量 UI、统一隐私策略 |

## 六、需要负责人拍板

1. 第一阶段是否确认只做“智能诊断助手”，不做泛聊天。
2. 是否允许桌面端保存用户自有模型 API Key。
3. 是否必须第一期就接服务端代理。
4. 默认发送上下文范围：
   - 推荐默认发送：应用版本、服务状态、配置摘要、最近错误码、健康检查结果。
   - 推荐默认不发送：截图、完整窗口标题、完整日志、token、密钥、用户原始敏感输入。
5. UI 入口：
   - 推荐 MVP：设备状态页诊断入口 + 开发者控制台命令。
   - 后续增强：独立“智能助手”页面。
