# 01 — 大模型智能诊断助手产品需求文档

> 状态：MVP 需求讨论稿  
> 优先级建议：P1  
> 目标版本建议：下一个 minor 版本  
> 功能性质：用户可感知功能、主进程网络能力、新 IPC、新配置、新 UI

## 一、功能概述

大模型智能诊断助手用于帮助用户和开发者理解 Neko Status 当前状态、错误原因和可执行的下一步建议。它读取本地已存在的状态、配置、日志和健康检查摘要，在用户确认后发送给配置的大模型服务，并以结构化方式返回诊断结论。

一句话目标：

> 把“散落在状态页、控制台、更新页和日志里的信息”整理成用户能看懂的诊断建议。

## 二、目标用户

- 普通用户：遇到上报失败、截图无效、更新失败时，希望知道怎么处理。
- 开发/维护者：联调 API、IPC、更新源和服务状态时，希望快速汇总上下文。
- 客服/支持人员：远程指导用户时，希望获得可复制的诊断摘要。

## 三、用户故事

1. 作为普通用户，我希望点击一次“智能诊断”，就能知道当前上报服务是否正常，以及如果异常应该先检查什么。
2. 作为开发者，我希望通过开发者控制台生成诊断摘要，快速定位 API、IPC、更新源或权限问题。
3. 作为重视隐私的用户，我希望发送给大模型前能看到将要发送的内容，并能取消。
4. 作为维护者，我希望模型失败不会影响状态上报、截图上传、更新检查等核心功能。

## 四、MVP 范围

### 4.1 设置能力

新增“大模型/智能诊断”设置区：

- 是否启用智能诊断。
- Provider 类型：`custom-compatible`，后续可扩展服务端代理。
- API endpoint。
- Model 名称。
- API Key。
- 请求超时时间，默认 30 秒。
- 每次上下文最大字符数，默认 16KB。
- 是否发送前预览，默认开启且不可在 MVP 关闭。
- 是否允许包含窗口标题，默认关闭。
- 是否允许包含最近日志，默认开启但自动脱敏。

### 4.2 诊断入口

MVP 建议提供两个入口：

- 设备状态页或服务页：按钮“智能诊断”。
- 开发者控制台：白名单命令 `llm status`、`llm test`、`llm diagnose`、`llm context`。

独立聊天页不进入 MVP，避免第一期范围过大。

### 4.3 上下文采集

上下文由主进程生成，renderer 不拼接敏感数据。默认包含：

- 应用版本、平台、运行模式。
- 服务运行状态、最近一次上报结果、连续失败次数、自动重启次数。
- 当前 CPU/内存/电池/网络连通性摘要。
- 截图启用状态、最近截图是否跳过、跳过原因、压缩结果摘要。
- 更新源模式、当前源类型、最近更新检查错误摘要。
- 配置摘要：仅包含影响诊断的非敏感字段。
- 最近日志：最多 100 行，且脱敏。
- 用户输入的问题。

默认不包含：

- 截图原图、缩略图、base64。
- 设备密钥、JWT、GitHub token、个人仓库 token、模型 API Key。
- 完整窗口标题、完整文件路径、完整 URL query。
- 任何 shell 输出中的未脱敏密钥。

### 4.4 模型输出格式

模型返回内容需要被渲染为结构化诊断结果：

- 当前结论：正常 / 需要关注 / 异常。
- 主要发现：最多 5 条。
- 建议操作：最多 5 条，只允许文字建议。
- 风险提醒：如果建议涉及隐私、密钥、重启、更新或删除数据，必须标记。
- 需要人工确认的问题：可选。
- 原始回答折叠展示，便于排障。

### 4.5 错误状态

必须覆盖以下错误：

- 未启用智能诊断。
- 未配置 API Key 或 endpoint。
- endpoint 不可达。
- 鉴权失败。
- 请求超时。
- 被限流。
- 返回非 JSON 或格式不兼容。
- 用户取消。
- 上下文为空或全部被隐私规则过滤。

## 五、非功能需求

### 性能

- 模型请求必须用户主动触发，不加入状态上报 tick。
- 同一时间最多 1 个活跃模型请求。
- 默认超时 30 秒，最大允许 60 秒。
- 单次上下文默认不超过 16KB，最大不超过 64KB。
- 请求失败最多自动重试 1 次，仅限网络瞬时错误。
- 模型调用不得阻塞主窗口渲染、服务启停、截图或更新检查。

### 安全

- 模型调用只能在主进程执行。
- API Key 不进入 renderer 日志，不进入模型上下文。
- 所有上下文发送前必须经过脱敏。
- 用户必须能查看即将发送的上下文。
- 模型回答不能直接触发配置修改、文件操作、更新安装或命令执行。

### 可维护性

- 新 IPC 必须先写契约和 schema。
- 新主进程能力独立为 `llm-service.js` 和 `llm.ipc.js`。
- renderer 通过 `llm-client.js` 调用。
- 页面逻辑放入 page/component，不写回 `app.js` 或 `app-ipc.js`。
- 新增开发者控制台命令必须更新测试和文档。

## 六、验收标准

### 成功路径

给定：用户已启用智能诊断并配置有效 endpoint、model、API Key。  
当：用户点击“智能诊断”并确认上下文。  
那么：系统展示结构化诊断结果，包含结论、发现、建议和风险提醒。  
验证方式：renderer VM 测试 + 手工联调。

### 隐私路径

给定：配置中存在设备密钥、JWT、更新源 token 和模型 API Key。  
当：用户生成诊断上下文。  
那么：预览内容和实际发送内容都不能包含原始密钥。  
验证方式：单元测试覆盖脱敏 helper。

### 失败路径

给定：endpoint 不可达或模型服务超时。  
当：用户发起诊断。  
那么：页面展示可理解的失败原因，不影响上报服务状态。  
验证方式：mock LLM service 单元测试 + 手工断网验证。

### 并发路径

给定：已有模型请求正在进行。  
当：用户再次点击诊断。  
那么：按钮保持加载/禁用状态，或提示已有请求进行中。  
验证方式：renderer VM 测试。

### 控制台路径

给定：开发者控制台可用。  
当：输入 `llm diagnose`。  
那么：命令走白名单注册，通过 IPC 调用主进程，不拼接动态 channel 或 shell。  
验证方式：`tests/unit/renderer-services.test.js`。
